    Why your RAG pipeline is failing in production.

    Most RAG implementations treat the LLM as a database. They don't. Language models are generators, not retrievers — and conflating the two roles produces systems that work in demos and fail under production load. The retrieval layer must be built with the same rigor as any other data system: deterministic, auditable, and bounded.

    Decoupling retrieval from generation is not a performance optimization — it's an architectural requirement. When they are decoupled, each can be tested, monitored, and improved independently. When they are fused, failures are opaque and fixes are guesses.

    Architecture before intelligence.

    The most common failure mode in AI projects is not a bad model — it's a bad architecture. Teams spend months fine-tuning LLMs and almost no time thinking about data flow, context management, and failure modes. Intelligence layered on top of a broken architecture is still broken.

    Design the data boundaries first. Define what information the model is allowed to see, and under what conditions. Build the retrieval layer as if the model doesn't exist yet. Only once that foundation is solid does the model selection become a meaningful decision.

  • /03

    Building AI assistants around structured enterprise data.

    Most enterprise data lives in SQL tables, not documents. But most AI assistant architectures are designed around unstructured text retrieval. The mismatch creates systems that can discuss documents fluently but cannot reliably answer "how many units were sold last quarter in region 3."

    The solution is hybrid retrieval: intent detection to classify query type, vector search for semantic/unstructured queries, SQL generation or direct lookup for structured ones. The orchestration layer decides the path — the model executes it. This produces systems that are both conversational and accurate on structured data.

  • /04

    Deterministic routing in AI applications.

    Non-determinism is the enemy of production AI systems. When the same input can produce different behavior on different runs, debugging becomes guesswork and monitoring becomes noise. Deterministic routing — classifying intent and hard-routing to pre-defined handlers — eliminates this problem at the architectural level.

    The trade-off is flexibility. A hard router cannot handle queries it was not designed for. But in enterprise contexts, this is a feature: the system should only do what it was designed to do. Graceful degradation is preferable to unpredictable hallucination.

  • /05

    Lessons from building FastAPI-based AI backends.

    FastAPI is an excellent foundation for AI service backends — async-native, type-safe, and fast enough for most AI workloads. But the architectural decisions that matter most have nothing to do with FastAPI itself: they are about how you structure data flow between the API layer, retrieval layer, and model layer.

    Key lessons: keep the model call at the very end of the request pipeline, not in the middle. Design the API contract to return structured objects, not raw model text. Build middleware for auth, rate limiting, and logging before the model sees any data. Treat the LLM as an implementation detail of a larger system.

  • /06

    What I learned experimenting with WebAssembly RAG.

    Running vector similarity search in a browser using WebAssembly is not a production architecture — but it is a clarifying experiment. It forces you to think precisely about what retrieval actually costs, where the bottlenecks are, and what a "small" knowledge base actually means in computational terms.

    The most useful insight: the embedding computation is the expensive part, not the similarity search. Pre-computing embeddings server-side and shipping them to the client is viable. Running the encoder in-browser is not. This changes how you think about edge AI architecture for retrieval tasks.

  • /07

    Designing role-aware AI systems.

    Role-based access control is a solved problem in traditional software. In AI systems, it is almost universally ignored. The result: AI assistants that inadvertently reveal cross-department data because no one designed retrieval boundaries into the system.

    The correct approach is to enforce access boundaries at the retrieval layer, not the API layer. The model should never receive context it is not permitted to have. Role filtering must happen before the vector store query, not after. Building this as middleware — rather than bolting it on after deployment — is what separates production AI from a proof of concept.

  • /08

    The illusion of the 10x engineer.

    A 10x engineer does not write 10x more code. They make 10x fewer decisions that lead to technical debt. The difference between a senior and junior engineer is not output volume — it is the ability to recognize which problems are not worth solving, which abstractions will create more complexity than they remove, and which "clever" solutions will become someone else's debugging nightmare at 2am.

    The best engineers I have worked alongside share one quality: they default to the simplest solution that could possibly work, and they are deeply suspicious of any solution that requires cleverness to understand. Complexity is a cost, not an achievement.
